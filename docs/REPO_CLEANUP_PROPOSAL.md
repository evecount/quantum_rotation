### 1.4 How the site is actually deployed

Commit `98ecf8e` ("ci: remove the docs/ Pages deploy workflow") records that
GitHub Pages is configured as a legacy branch build from `main` at the
repository root. The `docs/` deploy workflow was removed because the two
deploys raced and the loser decided what was live. So today:

- `index.html`, `constellation.html`, etc. in the **root** are the live site;
- `docs/*.html` are a frozen copy that no longer deploys anything;
- the root of the repo doubles as the web root, which is why the package,
  the notebooks, the pitch pages and the PDFs all share one directory.

## 2. Proposal: one source directory, one deploy step

### 2.1 Layout

```
site/                      single source of the published site
  index.html
  constellation.html
  simulation.html
  competition.html
  pitch.html
  404.html
  workbook.html            built artefact: Marimo export of notebooks/project_q_rotate.py
  .nojekyll
  assets/                  images + generated *.js (moved from ./assets)
  benchmarks/              the JSON the pages fetch (copied at build time from ./benchmarks)
  constellation/index.html, simulation/index.html, workbook/index.html   redirect stubs
docs/                      narrative docs only: 01–06, PRODUCT_PLAN, this file
```

Root keeps `README.md`, `LICENSE`, `CONTRIBUTING.md`, `pyproject.toml`,
`uv.lock`, `src/`, `tests/`, `benchmarks/`, `notebooks/` and the Marimo
scripts. Nothing HTML lives in the root any more.

### 2.2 Build/copy step

Two options, in order of preference.

**Option A: GitHub Actions deploy from `site/` (recommended).**
Restore a Pages workflow that uploads `site/` with `actions/upload-pages-artifact`
and deploys with `actions/deploy-pages`, and switch the repository's Pages
source setting from "Deploy from a branch" to "GitHub Actions". That removes
the root-vs-docs race for good because only one deploy exists. The workflow
can regenerate `site/workbook.html` from the notebook and copy the current
`benchmarks/*.json` into `site/benchmarks/` before uploading, so the served
numbers can never drift from the committed ones:

```yaml
- run: pip install -e ".[notebook]"
- run: marimo export html notebooks/project_q_rotate.py -o site/workbook.html
- run: cp benchmarks/*.json site/benchmarks/
- uses: actions/upload-pages-artifact@v3
  with: { path: site }
- uses: actions/deploy-pages@v4
```

**Option B: keep the legacy root build, delete the copies.**
If changing the Pages setting is not wanted before the finale, keep the root
as the web root and simply delete `docs/*.html`, `docs/assets/`,
`docs/benchmarks/`, `docs/provenance/`, `docs/workspaces/`, `docs/README.md`,
`docs/WHY_QROTATE_MATTERS.md`, `docs/.nojekyll`, `dynamite/workbook.html` and
`notebooks/project_q_rotate.html`, and add a one-line `scripts/build_site.sh`
that regenerates `workbook.html` and the `assets/*.js` mirrors. This is a
20-minute change with no settings change and no risk to the live site.

Either way, `workbook.html` should exist exactly once and be regenerated by a
command, not copied by hand.

### 2.3 Where the binaries go

| File(s)                                | Proposal |
| -------------------------------------- | -------- |
| `papers/*.pdf` (10.8 MB)               | Replace with `papers/README.md` listing the three arXiv IDs with links and one line each on why they matter. The PDFs are redistributable, but arXiv is the permanent host and nothing in the repo reads them. |
| Submission criteria PDF (1.0 MB)       | Move to a GitHub release asset (e.g. release `finale-2026`), link from `Competition.md`. |
| `Project_QRotate_One_Page_Summary_v3_OFFICIAL.pdf` (1.0 MB) | Attach to the same release and point the README badge at the release URL. If it must stay in-tree for the judges, track it with Git LFS. |
| `Project_QRotate_One_Page_Summary.html` (831 KB) | Do not commit it: it is an intermediate of `generate_one_page_summary.py`. Add it to `.gitignore` and regenerate on demand. |

Git LFS versus release assets: LFS keeps the files at their current paths (no
link changes) but every clone still downloads them unless `GIT_LFS_SKIP_SMUDGE`
is set, and GitHub LFS bandwidth is metered. Release assets cost nothing, are
versioned by tag and keep `git clone` small; the price is updating two links.
For a finale submission that judges will clone, release assets are the better
default; LFS only if a reviewer insists on an in-tree PDF.

Removing the binaries from the working tree does not shrink existing clones;
that would need a history rewrite, which the team already did once (see
`98ecf8e`) and should not repeat before the finale.

## 3. Suggested order

1. Add the `.gitignore` entry for the generated one-page HTML and stop committing it (no deletion, zero risk).
2. Replace `papers/*.pdf` with `papers/README.md` (10.8 MB gone, no links elsewhere to update).
3. Pick Option A or B for the site; do it in one PR that also updates the README project-layout tree.
4. Move the two remaining PDFs to a release and update the README badge and `Competition.md`.

Each step is a separate small PR so the live site can be checked after step 3
before anything else moves.
